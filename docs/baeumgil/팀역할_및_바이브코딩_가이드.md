# 배움길 팀 역할 및 바이브 코딩 가이드

- **작성일**: 2026-10-24
- **목적**: 각 팀원이 자기 담당 범위를 AI 코딩 도구에 전달하고, 같은 제품을 충돌 없이 공동 개발하기 위한 작업 기준
- **관련 문서**: [기획서](./기획서.md) · [PRD](./PRD.md) · [해커톤 MVP 개발 계획](../superpowers/plans/2026-10-24-baeumgil-hackathon-mvp.md)
- **문서의 범위**: 팀 역할·협업 방식 정리. 앱 구현·DB 도입·외부 배포가 완료되었다는 의미가 아니다.

## 1. 확정한 역할과 이번 문서의 제안

| 팀원 | 확정한 역할 | 이 문서에서 정리한 작업 영역 |
|---|---|---|
| PM | 프로젝트 관리 | 범위·우선순위·자료·검수 조율·시연·완료 판정 |
| 지훈님 | DB 관리 및 백엔드 | 공통 데이터 계약, 저장·조회, 서버·AI 공급자 연결, 회기·일지·월별 집계 |
| 예서님 | FE | 멘티·멘토 화면, 화면 전환, 공통 UI 상태, 백엔드·학습 엔진 연결 |
| 다은님 + 수영님 | 두 명이 한 세트로 공동 개발 | **제안 범위**: 학습 엔진·문항 생성·학습 근거 요약·AI 프롬프트와 출력 검증 |

PM·DB/백엔드·FE·다은님과 수영님의 공동 작업 방식은 팀이 정한 내용이다. 다은님·수영님의 구체적인 기능 배정은 남은 영역을 기준으로 이 문서가 제안한 기본안이다. 두 분의 개인별 세부 담당은 아직 정해진 것으로 취급하지 않는다.

첫 공동 목표는 다음 흐름이 한 앱 안에서 동작하는 것이다.

**기출 풀이 → 오답 개념 확인 → 필요한 기초 연습 → 유사 문제 → 원래 기출 재도전 → 새 적용 확인 → 멘토 확인·일지**

## 2. 역할별 책임과 첫 산출물

### 2.1 PM

**책임**

- PRD와 개발 계획에서 이번에 구현할 P0 범위를 관리한다.
- 대표 문항 하나와 사용할 시연 시나리오를 정한다.
- 기출·공식 정답·사용 범위·센터 양식 등 필요한 자료의 확보와 검수를 조율한다.
- 기획자의 실제 활동기관·프로그램·업무를 확인해 발표 근거를 정리한다.
- 팀원 사이의 미결정 사항과 막힌 일을 정리하고 우선순위를 결정한다.
- 통합 결과를 사용자 관점에서 조작하고 PRD의 수용 기준 충족 여부를 확인한다.
- 시연 데이터, 실제 AI 결과, 검증 전 기대 효과를 구분해 발표를 준비한다.

**첫 산출물**

1. 대표 문항 1개와 정답·관련 개념·예상 보충 경로
2. P0 작업 목록과 담당 영역
3. 자료 확보 상태와 결정이 필요한 항목 목록
4. 한 학생의 학습부터 일지까지 이어지는 시연 순서

PM은 화면 수나 코드 작성량보다 **한 경로가 연결되는지, 각 단계의 완료 기준이 맞는지**를 확인한다. 기술적 연결은 지훈님과 예서님이 공동으로 확인하고, 제품 범위와 우선순위 충돌은 PM이 정리한다.

### 2.2 지훈님 — DB 관리 및 백엔드

**책임**

- 학생·문항·과제·학습 경로·응답·노출·회기·일지·AI 결과의 데이터 구조를 관리한다.
- 데이터 ID, 상태 이름, 오류 형식, 저장 버전과 요청·응답 계약을 정리한다.
- 공통 저장·복구·중복 방지와 조회 기능을 구현한다.
- 서버 실행 환경, 실제 AI 공급자 호출, 비밀 키 보관을 담당한다.
- 실제 회기와 자율 학습 기록을 구분하고 일지 확정·개정·철회·월별 합산 규칙을 구현한다.
- 다은님·수영님이 제공하는 학습 엔진·사실 요약·AI 검증 모듈을 저장·서버 처리에 연결한다.
- 예서님에게 연결 가능한 기능, 입출력 예시, 오류와 준비 상태를 전달한다.

**첫 산출물**

1. 공통 데이터 형식과 예시 응답
2. 가명 학생·문항·학습 기록을 넣고 다시 읽을 수 있는 저장 경로
3. 실제 AI 호출 가능 여부 확인
4. FE가 먼저 사용할 수 있는 저장·조회 및 AI 호출 인터페이스

**주의할 경계**

- 실제 AI 호출·인증·서버 시간 초과는 지훈님이 담당한다.
- 교육적 프롬프트와 AI 출력의 근거 검증 규칙은 다은님·수영님과 연결한다.
- 채점·학습 분기 규칙을 백엔드에서 따로 다시 만들지 않는다. 동일한 학습 엔진을 사용한다.
- 화면용 상태·오류 표시는 예서님에게 전달하고 직접 UI 파일을 병행 수정하지 않는다.

### 2.3 예서님 — FE

**책임**

- 역할 선택, 문제은행, 멘티 학습, 결과 요약, 멘토 대시보드, 수업 준비, 일지, 월별 대장 화면을 구현한다.
- 현재 단계, 정답·오답·모름, 도움·중단, 저장·AI 요청 상태를 사용자가 이해할 수 있게 표시한다.
- 공통 화면 전환과 클라이언트 상태 연결을 관리한다.
- 다은님·수영님의 엔진을 호출하고 반환 결과를 표시한다.
- 지훈님의 저장·조회·서버 기능을 연결한다.
- 실제 연결 전에는 합의한 형식의 임시 데이터를 사용하고, 실제 데이터로 교체할 수 있는 경계를 유지한다.
- 모바일·키보드 조작·오류 복구·멘티와 멘토 화면 분리를 확인한다.

**첫 산출물**

1. 임시 데이터로 처음부터 끝까지 조작할 수 있는 멘티 학습 화면
2. 같은 기록을 보는 멘토 대시보드와 수동 일지 화면 뼈대
3. 호출 중·실패·빈 데이터·미검토 상태 표시

**주의할 경계**

- 화면에서 정답이나 다음 학습 단계를 별도로 계산하지 않는다.
- API 응답을 화면마다 다른 데이터 형식으로 재정의하지 않는다.
- 실제 AI 키를 FE에 넣지 않는다.
- 학습 화면의 일시적 선택 상태와 저장해야 하는 학습 기록을 구분한다.
- 서버 DB 또는 로컬 저장 방식은 호출 어댑터 뒤에 두고 화면 곳곳에 저장 코드를 만들지 않는다.

### 2.4 다은님 + 수영님 — 학습 엔진·AI 공동 개발 제안

**공동 책임**

- 정답 비교와 개념 확인·기초·유사·재도전·새 적용의 상태 전이를 구현한다.
- 승인된 문항 틀의 숫자 변경, 정답 계산, 선택지·문항 조건 검사를 구현한다.
- 학생의 전체 노출 이력으로 새 적용 문항 여부를 판정한다.
- 직접 응답·관계상 추정·추가 확인 필요를 구분해 학습 근거를 정리한다.
- 학습 결과에서 멘토가 읽을 수 있는 사실 요약을 만든다.
- AI 수업안·일지 문장의 입력 구성, 프롬프트, 출력 형식과 근거 참조 검증을 담당한다.
- 정상 흐름과 모름·반복 미달·건너뛰기·문항 소진·도움 사용의 검증 자료를 만든다.

**첫 산출물**

1. 대표 문항 하나의 학습 경로를 코드로 재현하는 엔진
2. 입력과 결과가 고정된 예시 데이터·검증 결과
3. 수업안과 일지 문장용 AI 입력·출력 예시

**둘이 함께 작업하는 방식**

- 한 사람은 현재 작업의 작성, 다른 사람은 규칙·예외·검증을 맡는다. 작업 묶음이 끝나면 교대할 수 있다.
- 잠시 나눠 작업한다면 ‘학습 엔진·생성’과 ‘학습 요약·AI 검증’으로 파일을 구분한다. 개인별 담당은 두 분이 정하고 작업 기록에 남긴다.
- 각자 별도의 코딩 에이전트를 쓸 경우에도 수정 파일을 나눈다. 같은 `engine.js`를 동시에 수정하지 않는다.
- 두 사람이 만든 결과물은 공동으로 한 번 실행하고 지훈님·예서님에게 전달한다.

**주의할 경계**

- 실제 모델 호출·인증 코드는 지훈님 영역과 중복 구현하지 않는다.
- 화면은 예서님, 저장 구조·서버·일지 확정 규칙은 지훈님이 담당한다.
- AI가 정답·숙달·출석·활동 시간을 결정하도록 만들지 않는다.
- 문제 생성기의 검증 통과가 교육적 난이도 검증을 뜻한다고 표현하지 않는다.

| 통합·수용 기준·발표 | PM 진행 | 각 기능 담당자가 수정·기술 확인 | PRD AC별 결과·시연 범위 |

## 4. 파일 담당 원칙

아래는 개발 계획의 신규 앱 경로 `apps/baeumgil/`를 기준으로 한 예정 소유권이다. 기존 소스를 재사용하거나 실제 구조가 달라지면 같은 책임 단위로 대응시킨다.

| 파일·영역 | 담당 |
|---|---|
| `docs/baeumgil/`의 제품·역할 문서, 개발 우선순위 | PM |
| `server.mjs`, `server/`, 실제 DB 스키마·마이그레이션·시드가 생길 경우 해당 파일 | 지훈님 |
| `public/src/domain/contracts.js`, `public/src/state/persistence.js` | 지훈님 |
| `public/src/mentoring/logs.js` | 지훈님 |
| `public/index.html`, `public/styles.css`, `public/app.js` | 예서님 |
| `public/src/ui/`, `public/src/state/store.js`, `public/src/ai/client.js` | 예서님 |
| `public/src/learning/`, `public/src/content/` | 다은님·수영님 |
| `public/src/mentoring/summary.js`, `public/src/ai/contracts.js`, AI 프롬프트 파일 | 다은님·수영님 |
| 각 영역의 테스트 | 해당 기능 담당자 |
| `package.json`, 공통 실행 설정 | 초기 설정은 지훈님, FE 요구는 예서님과 함께 확인 |
| 공유 테스트 자료 `tests/fixtures.js` | 초안은 다은님·수영님, ID·엔티티 형식 변경은 지훈님과 확인 |

- 파일 담당은 수정 충돌을 줄이기 위한 기준이다. 다른 영역의 문제가 보이면 재현 방법·필요 변경을 담당자에게 전달한다.
- 공통 ID·필드·상태·함수 이름은 담당자가 관련 팀원과 영향을 확인한 뒤 바꾼다.
- 두 기능이 같은 파일을 수정해야 하면 한 사람이 반영하고 나머지는 변경 요구를 전달한다.
- 제품 범위를 바꾸는 결정은 PM이 정리하고, 데이터·인터페이스 변경은 지훈님이 계약에 반영한다.

## 5. DB 담당과 MVP 저장 방식의 구분

현재 PRD는 한 브라우저의 로컬 저장을 MVP 기준으로 삼는다. **지훈님이 DB·백엔드를 맡는다는 결정만으로 실제 서버 DB·인증·다기기 동기화까지 P0에 추가하지 않는다.**

지훈님은 로컬 시연에서도 데이터 구조, 저장·복구 계약, 버전·중복 방지, 실제 AI 서버, 회기·일지 규칙을 담당한다. 예서님은 이를 호출해 화면에 연결한다.

실제 서버 DB를 이번에 연결하기로 팀이 정하면 다음 내용을 먼저 기록한다.

1. 사용할 서버·DB 환경과 공용 실행 방법
2. 데이터의 최종 원본이 로컬인지 서버인지
3. FE의 읽기·쓰기 방식과 저장 완료 판정
4. ID·중복 제출·버전 충돌·노출 이력 처리
5. 기존 시연 데이터의 이동·초기화 방식
6. 통신 실패 때 보여 줄 상태와 진행 가능한 범위
7. 영향을 받는 PRD·개발 계획·수용 기준 변경

저장 방식이 확정되기 전에는 각자가 다른 DB·로컬 저장을 독립적으로 붙이지 않는다. DBMS나 프레임워크 선택은 현재 확정된 것으로 기재하지 않는다.

## 6. 시작 전에 맞출 공통 계약

지훈님이 공통 계약 초안을 정리하고 예서님·다은님·수영님이 자신의 연결에 필요한 값을 확인한다. PM은 제품 범위와 충돌하는지 확인한다. 기존 PRD와 개발 계획의 데이터·함수 이름을 출발점으로 삼는다.

| 합의할 것 | 예시·확인 항목 |
|---|---|
| 대표 데이터 | `learner-1`, `mentor-1`, `assignment-1`, `path-1`, 원 문항·응답 ID |
| 학습 단계 | `original_attempt`, `concept_check`, `foundation_practice`, `similar_practice`, `original_retry`, `transfer_check` |
| 종료·검토 상태 | `completed`, `needs_mentor`, `paused`, `not_measured` |
| 응답 | `correct`, `incorrect`, `abstained`; 도움·힌트·정답 노출은 별도 기록 |
| 엔진 호출 | 개발 계획의 `applyLearningCommand(state, command, {catalog,rng})`와 반환 `{state,events}` |
| 사실 요약 | 최초·재도전·새 적용을 구분하고 원 응답·근거 ID 유지 |
| 저장 호출 | 로컬·서버와 관계없이 저장 실패·revision 충돌·재개 결과 제공 |
| AI 호출 | 요청 ID·입력 버전·근거 목록, 15초 실패·취소·늦은 응답 처리 |
| 일지 | 실제 회기, 출석·활동 분·검토, 개정·철회, 최신 유효본 합산 |

전달 형태는 함께 정하되 같은 기능에 브라우저 함수와 HTTP API를 각자 독립 설계하지 않는다. 실제 서버 API가 생기면 지훈님이 요청·응답 예시를 남기고, FE는 같은 형식의 임시 응답으로 먼저 개발할 수 있게 한다.

### 공유할 최소 자료

- 정상 요청·응답 1세트
- 오답·모름·멘토 확인 필요 결과
- 빈 데이터·저장 실패·충돌 결과
- AI 요청 중·성공·실패·시간 초과 결과
- 일지 초안·확정·개정·철회 결과

임시 데이터와 실제 결과를 화면과 기록에서 구분한다. 프롬프트·응답·화면·DB에 서로 다른 학생 ID나 단계 이름을 만들지 않는다.

## 7. 같이 진행하는 작업 순서

> **시간 기준**: 1·2차 목표는 예선 PDF 마감(10/24 19:00) 전까지 끝낸다. 3·4차 목표는 본선 전까지 진행하고, 5차 목표는 대회 이후로 둔다. 시각별 표는 개발 계획 0절을 따른다.

### 1차 목표: 서로 기다리지 않고 시작

- **PM**: 대표 문항·시연 순서·자료 상태를 정리한다.
- **지훈님**: 공통 데이터·저장 계약과 실제 AI 실행 가능 여부를 확인한다.
- **예서님**: 계약에 맞는 임시 데이터로 학습 화면과 멘토 화면 뼈대를 만든다.
- **다은님·수영님**: 대표 문항의 엔진·문항 생성·검증 자료와 AI 입출력 예시를 만든다.

### 2차 목표: 학습 흐름 첫 통합

**예서님 화면 → 다은님·수영님 엔진 → 지훈님 저장 경로 → 화면 결과**

PM이 한 문항을 오답 처리해 개념 확인·기초·유사·재도전·새 적용까지 직접 조작한다. 정상 흐름이 연결되면 모름·중단·도움·반복 미달을 확인한다.

### 3차 목표: 멘토 운영 연결

**같은 학습 기록 → 근거 요약 → 멘토 대시보드 → 회기 메모·수동 일지 → 대장**

학생이 푼 기록을 따로 입력하지 않고 대시보드와 일지에서 재사용하는지 확인한다. AI가 없어도 수동 기록이 가능한 상태를 먼저 만든다.

### 4차 목표: 실제 AI 연결

**다은님·수영님 입력·검증 → 지훈님 실제 호출 → 예서님 상태·결과 표시**

실제 AI 연결 가능성 점검은 초기에 진행한다. 통합 단계에서는 방금 생성한 학습 기록으로 수업 제안과 일지 문장을 생성한다. 실패했을 때 기존 기록과 수동 작성이 유지되는지 확인한다.

### 5차 목표: 범위 확대와 시연 검증 (대회 이후)

검수된 기출 10문제·2유형으로 확장하고, 실제 양식과 PRD AC-01~20을 확인한다. 자료·AI·검증이 미완료면 PM이 시연 범위와 남은 항목을 명확히 표시한다.

## 8. 바이브 코딩 공통 규칙

1. AI에게 기획서·PRD·개발 계획·이 역할 문서를 먼저 읽게 한다.
2. 이번 작업의 담당 영역과 만들 결과물 하나를 지정한다.
3. 기존 파일과 변경 사항을 확인하게 하고, 다른 팀원의 작업을 덮어쓰지 않게 한다.
4. 각 AI가 앱 전체나 저장 구조를 새로 만들지 않도록 담당 파일·인터페이스를 알려 준다.
5. 공통 계약 변경은 관련 담당자와 합의한 뒤 반영한다. 필요한 변경을 기록하는 동안 독립적으로 가능한 작업은 계속한다.
6. 연결 전에는 합의한 임시 데이터로 개발하고 실제 연결 여부를 구분한다.
7. 엔진·집계·저장·AI 예외처럼 오류 영향이 큰 부분은 의미 있는 검증을 실행한다. 화면은 핵심 흐름을 직접 조작한다.
8. AI가 ‘완료’라고 말한 것만으로 넘기지 않고 실행 방법·실제 검증 결과·남은 문제를 전달한다.
9. API 키·실제 학생 정보·기출 이용 조건을 임의로 만들어 넣지 않는다.
10. 배포·자료 공유·DB 변경은 팀이 정한 실제 작업 범위와 환경을 따른다. 설정 파일·라이브러리 선택을 팀별로 따로 바꾸지 않는다.

```text
실제 모델 호출·인증과 화면을 별도로 중복 구현하지 마라.

작업 후 변경 파일, 엔진 입출력, 정상·예외 검증 결과, AI 계약과 필요한 연결 작업을 보고하라.
```

```text
- 호출 방법·입출력 예시:
- 임시 데이터 / 실제 연결 여부:
- 실행·검증 결과:
- 상대 담당자에게 필요한 연결:
- 막힌 점·결정 필요 사항:
```

### 통합 확인

- [ ] 같은 학생·문항·경로 ID로 FE·엔진·저장이 연결된다.
- [ ] 한 문항의 오답부터 새 적용 확인까지 실제 조작할 수 있다.
- [ ] 최초 응답과 도움·노출 이력이 보존된다.
- [ ] 같은 학습 결과가 멘토 대시보드와 일지에서 보인다.
- [ ] 실제 회기 확인 전 출석·활동 시간이 만들어지지 않는다.
- [ ] AI 실패 뒤에도 학습과 수동 일지 작성이 가능하다.
- [ ] 확정·개정·철회된 일지가 대장에 중복 합산되지 않는다.
- [ ] 공식 기출·자체 제작·임시 데이터·실제 AI 결과를 구분한다.
- [ ] 기출 수량·양식 검수·AC 결과를 확인한 범위만 완료로 보고한다.

## 11. 미결정 사항과 변경 규칙

| 항목 | 현재 상태 | 정리 담당 |
|---|---|---|
| PM·지훈(DB/백엔드)·예서(FE)·다은/수영 공동 작업 | 팀이 확정 | PM |
| 다은·수영의 학습 엔진·AI 기능 배정 | 이 문서의 제안 기본안 | PM + 다은님·수영님 |
| 다은·수영 내부의 작성·검증·파일별 담당 | 두 분이 작업마다 정함 | 다은님·수영님 |
| 실제 서버 DB 도입 여부·종류 | 미정; 현재 PRD는 로컬 저장 기준 | 지훈님 제안, PM 범위 정리, 예서님 연결 확인 |
| FE·서버 프레임워크·실제 저장소 구조 | 기존 소스·실행 환경 확인 후 정리 | 지훈님·예서님 |
| 실제 AI 제공자·모델·인증 | 무료 등급 API로 결정, 기본안 Google Gemini; 키 발급·모델 확인 필요 | 지훈님 + 다은님·수영님 |
| 플렉스튜디오 | 사용하지 않음 | 팀 확정 |
| 기출·양식·활동 경험의 근거 범위 | 자료별 확인 필요 | PM + 관련 경험자·담당자 |

범위나 계약을 바꾸면 역할 문서·PRD·개발 계획 중 영향을 받는 문서를 함께 갱신한다. 팀원에게 전달하지 않은 데이터 구조·저장 방식 변경을 각자의 AI가 독립적으로 확정하지 않도록 한다.
