# 배움길 최종 발표 고도화 계획

작성일: 2026-10-24 / 대상: ver2 / 상태: 제안 계획, 추가 구현 전

## 1. 목표와 일정 기준

**오답 기록에 맞는 AI 보충 문제를 만들고, 코드로 검증한 뒤 연습과 멘토의 다음 수업으로 연결하는 과정을 실제로 보여 준다.**

사용자 확인: 최종 자료 제출은 12시이며, 제출 후에도 최종 발표 전까지 수정 가능하다. 행사 안내 11쪽: 본선 발표 5분·질의응답 5분. 최종 발표 시각은 아직 확인하지 않았으므로 아래는 제출·발표 시점 기준으로 배치한다.

- 12시 제출본은 그때까지 실제로 검증된 구현과 확보한 근거만 담는다.
- 제출 이후 개발은 별도 작업본에서 계속하고, 검증을 통과한 내용만 최종 발표본에 반영한다.
- 발표 60분 전 기능 고정을 권장한다. 이후에는 시연 오류 수정·캡처·대본 일치·리허설에 집중한다.
- 기능이 시간 안에 통합되지 않으면 범위를 줄인다. 미완료 기능은 계획으로 표시한다.

## 2. 현재 확보한 것과 보완할 것

| 현재 | 최종 발표까지 보완할 것 |
|---|---|
| 6개 영역 첫 수준 확인, 선수 개념 분기 | 두 개념 AI 추가 연습과 정답 검증 |
| 진단 기록 기반 로드맵·개념 지도 | AI 문제 출처와 풀이 기록을 멘토 화면에서도 확인 |
| 기존 문항·기출·틀 기반 보충, 재도전·새 문제 결과 구분 | 전체 시연을 끊김 없이 연결하고 실패 대체 검증 |
| AI 수업 제안·활동일지 초안 | 실제 호출·멘토 검토가 이어지는 한 사례 확보 |
| 가명 역할 선택, 브라우저 저장 | 현재 구현 범위와 기기별 저장 제약을 정확히 설명 |
| 팀원의 학생 5명 수학 멘토링 경험 | 경험의 상세 확인 및 팀원 멘토의 실제 사용 의견 |
| 중간발표 11장·질의응답 26문항 | 5분 발표와 5분 질의응답에 맞춘 최종 자료 |

기능·플랫폼 활용·구현 정도가 각각 20점이라는 행사 안내를 참고해, 새 메뉴 수보다 실제 동작·API 활용 근거·안정적인 연결을 우선한다. 주최 측이 말하는 ‘플랫폼 기능 활용’의 정확한 평가 범위는 멘토에게 확인하며, Gemini API를 썼다는 사실만으로 해당 배점을 확보했다고 가정하지 않는다.

## 3. 필수 고도화: P0

### P0-1. 검증 가능한 AI 추가 연습

기존 설계 범위를 유지한다. 적용 개념은 **일차식 계산·동류항 정리** 두 개다.

1. 해당 개념의 기존 진단·보충 응답을 읽는다.
2. AI가 허용된 일차식 구조·계수·선택지 후보를 만든다.
3. 코드가 ax+b로 계산해 정답·정답 유일성·동치 선택지 중복·범위를 검사한다.
4. 통과한 문제만 보여 주고, 풀이도 검증된 식으로 코드가 만든다.
5. 최대 5초 생성 대기 후 기존 문제로 대체한다. 기다리는 동안에도 기존 문제로 바로 갈 수 있다.
6. 문항·답변·출처를 별도 기록으로 저장하고 새로고침 후 복원한다.

**완료 기준**

- 두 개념 각각 실제 AI 응답→검증→제출→해설→저장/복원이 성공한다.
- 잘못된 정답·동치 중복 선택지·범위 밖 식이 출제되지 않는다.
- 실패·이동 후 늦은 응답·연속 클릭에도 현재 문항이나 기존 기록이 덮어써지지 않는다.
- 첫 수준 확인과 정식 기출 학습 엔진은 유지한다. AI 정답이 최초 진단 티어나 기출 독립 적용률을 올리지 않는다.

상세 설계: [AI 보충 설계](../superpowers/specs/2026-10-24-ai-supplementary-practice-design.md), [구현 계획](../superpowers/plans/2026-10-24-ai-supplementary-practice.md).

### P0-2. 멘토가 결과를 확인할 수 있는 연결

AI 문제를 푸는 데서 끝나지 않도록, 같은 진단·개념의 멘토 화면에서 다음을 확인한다.

- 어떤 기존 응답을 근거로 추가 연습을 제공했는지.
- AI 추가 연습에서 무엇을 풀었고 맞힘·오답·모름이 무엇인지.
- 최초 진단과 추가 연습 결과가 각각 무엇인지.
- 다음 수업에서 확인할 개념과 기존 기출 학습으로 이동할 위치.

기존 로드맵·학습 기록·AI 수업 제안 기능을 재사용한다. AI 연습을 기존 기출 경로의 완료로 처리하거나, AI 연습 후 원래 진단 응답을 재채점하지 않는다. 별도 연습 결과를 표시하는 데 필요한 최소 UI만 추가한다.

**완료 기준:** 멘티가 AI 문제를 푼 뒤 같은 브라우저에서 멘토로 전환했을 때 동일한 문항·결과가 보이고, 기록을 근거로 수업을 준비하는 흐름을 설명할 수 있다. 서로 다른 기기에서 기록이 동기화된다고 시연하지 않는다.

### P0-3. 실패해도 계속되는 시연

- AI 미설정·네트워크 실패·429·검증 실패·시간 초과: 준비된 문제로 이동.
- 역할·과목·카드 이동: 요청 취소, 늦은 결과 무시.
- 새로고침: 미제출 문제와 제출 결과 복원.
- 저장 충돌: 다른 탭의 최신 기록을 덮어쓰지 않음.
- HTTP LAN 주소: ID 생성과 문제 풀이 정상 동작.

시연에 사용할 별도 가명 상태와 캡처/짧은 녹화본을 준비한다. 실패 대체 장면도 실제 기능으로 보여 줄 수 있게 한다. 녹화·저장 예시는 실시간 호출과 구분해 소개한다.

### P0-4. 실제로 확인한 근거 확보

**팀원 멘토에게 확인할 내용**

1. 학생 5명 지도 경험의 대상·기간·방식. 학교 밖 청소년/검정고시 대상이었는지는 별도 확인.
2. 학생의 수준을 처음 어떻게 파악했는지.
3. 문제 준비와 수업 기록에서 직접 겪은 어려움.
4. 배움길에서 유용한 정보와 부족하거나 오해하기 쉬운 부분.
5. 실제 수업에 쓰려면 무엇이 먼저 보완되어야 하는지.

팀원 멘토 1명의 점검은 **내부 사용성 피드백**으로 보고한다. 학생 5명으로 배움길의 학습 효과를 검증했다고 설명하지 않는다. 실제 인터뷰나 학생 테스트는 당사자와 적절한 절차를 마련한 경우에만 진행하며, 부족한 시간을 맞추려고 결과를 만들지 않는다.

**코드·API 검증 기록**

- 수학 검사: 허용 사례와 오답/중복/범위 위반 사례를 명시적으로 테스트.
- 실제 AI 호출: 가능하면 개념별 5회씩, 총 10회 생성 시도에 대해 검증 통과·기존 문항 대체·지연 시간을 기록. 이 수는 소규모 기술 점검이며 교육적 정확도 추정으로 사용하지 않는다.
- 시간·비용: 실제 모델·요청 수·응답 시간·확인 가능한 사용량만 기록. 확인하지 못한 비용 수치를 만들지 않는다.
- 실제 AI 설정이 없다면 모의 공급자 검사와 fallback 검증까지라고 분명히 보고한다.

**완료 기준:** ‘좋아 보인다’ 대신 어떤 입력에서 무엇을 확인했는지 표 한 장과 멘토의 실제 의견을 제시한다. 잘못된 후보가 생성된 경우도 숨기지 않고, 검증에서 거부해 기존 문항으로 대체된 결과로 기록한다.

## 4. 여유가 있을 때: P1

| 후보 | 추가하는 조건 | 완료 기준 |
|---|---|---|
| AI 연습 뒤 관련 기출 학습 이동 버튼 | P0가 모두 통합되고, 기존 과제/학습 경로를 안전하게 재사용할 수 있을 때 | 최초 진단을 수정하지 않고 관련 기출의 기존 학습 화면으로 이동 |
| 수업 준비용 한 화면 요약 | 멘토 피드백에서 정보 찾기가 어렵다는 문제가 확인될 때 | 막힌 개념·추가 연습 결과·다음 확인 질문을 한곳에서 확인 |
| 문항·선수 관계의 집중 검토 | 시연에 쓰는 경로의 표기나 연결이 부정확할 때 | 시연 경로의 개념·출처·정답을 실제로 대조한 기록 |

시연 핵심 경로의 잘못된 정답·연결은 여유 기능이 아니라 즉시 수정해야 할 P0 오류다. P1의 집중 검토는 검토 범위를 추가로 넓히는 일이다.

## 5. 최종 발표 뒤로 미룰 것: P2

- 실제 계정/인증, 서버 DB, 여러 기기 동기화, 센터별 권한.
- 수학 전 범위 AI 생성, 국어·영어 등 다른 과목.
- 새로운 학생 모델 학습·표준화 진단·장기 학습 효과 실험.
- 멘토 홈·문제 풀이 화면의 전면 디자인 변경.
- 과금·기관 도입·조달 연계와 광범위한 콘텐츠 배포.

이 기능들은 필요하지만 이번 발표의 핵심 흐름보다 범위가 크다. 만약 최종 평가에서 서로 다른 기기의 멘토·멘티 협업을 필수로 요구한다면, 바로 개발을 늘리기보다 AI/발표 범위와 함께 우선순위를 다시 정한다.

## 6. 단계별 진행과 중단 기준

| 단계 | 진행할 일 | 다음 단계로 넘어가는 조건 |
|---|---|---|
| 1. 기준 버전 확인 | 다른 세션 활동 확인, 미커밋 LAN·ID 수정 보존, 시연 기준 상태 확인 | 기존 진단·문제 풀이가 정상, 작업 충돌 없음 |
| 2. AI 생성·검증 | 수학 검증기 → API → 저장 → UI 연결 | 두 개념의 생성과 fallback이 동작 |
| 3. 전체 연결 | 멘티 연습 → 멘토 확인 → 수업 제안·기록 | 실제 결과가 유지되고 역할 변경/새로고침 통과 |
| 4. 근거 수집 | 실제 호출 점검, 멘토 피드백, 실패 시나리오 확인 | 수치·의견·한계를 자료로 정리 가능 |
| 5. 12시 제출본 | 5분 PPT·PDF·대본·Q&A를 구현 상태와 일치시킴 | 제출 파일에서 계획을 구현 성과로 설명하지 않음 |
| 6. 제출 후 개선 | P0 오류 수정과 통과한 P1만 반영 | 전체 점검 재통과, 기존 제출본 별도 보존 |
| 7. 발표 60분 전 | 기능 고정, 영상/캡처·발표본·시연 상태 고정 | 발표자가 동일한 순서로 2회 이상 리허설 |

중단 기준:

- 생성 문제를 안전하게 검증할 수 없으면 범위/식 구조를 줄인다. 자유 생성으로 우회하지 않는다.
- AI API가 불안정해도 기존 문항 대체가 안정적이면 그 사실을 포함해 시연한다.
- 12시까지 통합되지 않은 기능은 제출본에서 ‘향후’로 둔다.
- 발표 60분 전 P1이 불안정하면 발표본에서 빼고 검증된 버전으로 진행한다.
- 실제 학습 효과가 측정되지 않았으면 기능·기술 검증과 사용성 의견까지만 성과로 제시한다.

## 7. 팀 작업 배치 제안

실제 담당자는 팀에서 정한다. 다음은 서로 기다리는 시간을 줄이기 위한 역할 제안이다.

| 역할 | 결과물 | 공유 파일 편집 시 주의 |
|---|---|---|
| 핵심 개발 | AI 수학 검증·서버·상태·UI의 연결 | app.js/server.mjs/공통 계약은 통합 담당 중심으로 순차 편집 |
| 콘텐츠·검증 | 두 개념의 정상/오류 사례와 기출 연결 점검 | 콘텐츠 변경과 엔진 변경을 사전 공유 |
| 멘토 경험자 | 실제 경험의 상세와 프로토타입 피드백 | 사용 의견과 효능 검증을 구분 |
| 발표·자료 | 기사·통계 근거, 5분 PPT, 기술 구조도, Q&A | 구현팀의 완료 목록에 맞춰 문구 갱신 |
| 시연·기록 | 생성/대체 측정표, 캡처·짧은 영상, 리허설 | 실행 중인 다른 사람의 저장 데이터를 초기화하지 않음 |

이 표는 제안일 뿐 다른 세션에 작업을 보내거나 팀원에게 연락한 상태는 아니다.

## 8. 5분 최종 발표 구성

| 시간 | 내용 | 보여 줄 근거 |
|---|---|---|
| 0:00~0:45 | 문제 배경과 대상 | 기존 기사·학업중단 그래프·검정고시 수요 중 핵심 자료 |
| 0:45~1:15 | 현장 경험·문제·기존 방식과의 차이 | 확인된 멘토 경험, 네 가지 문제, 타사 비교의 한정된 범위와 해결 흐름 |
| 1:15~1:45 | 기술 구조와 AI의 역할 | 기록→Gemini→코드 검증→출제/기존 대체 구조도 |

## 9. 발표 전 최종 확인

- [ ] 기존 전체 테스트와 추가 테스트 통과, 콘텐츠 검사 오류 없음.
- [ ] 실제 AI 호출 성공과 기존 문항 대체를 각각 확인.
- [ ] LAN 접속·새로고침·역할 전환·저장 충돌 확인.
- [ ] 예시 이름·데이터가 가명이며, 제출본과 시연 기능 일치.
- [ ] 최초 진단과 추가 연습, 기출과 AI/자체 제작 문제를 구분.
- [ ] 미검증 학습 효과·기관 구매·전체 콘텐츠 이용권을 확정 성과로 쓰지 않음.
- [ ] 팀원이 학생 5명을 수학 멘토링한 경험과 제품을 5명에게 검증한 사실을 혼동하지 않음.
- [ ] 12시 제출본·최종 발표본·백업 영상/캡처를 구분해 보관.
- [ ] 실제 발표 길이 5분에 맞춰 2회 이상 리허설.

현재 계획 작성으로 제품 코드·서버·기존 기록을 변경하지 않았다. 세부 시간과 담당 배치는 팀의 가용 인원 및 실제 발표 시각 확인 후 조정한다.
